# Riot Sign-On exploratory research

Research date: 2026-10-29. This assessment combines official sources with repository inspection. It is not an accepted design, implementation plan or amendment to [ADR-0001](adr/0001-self-host-baseline.md). The [productization plan](PRODUCTIZATION_PLAN.md) preserves standalone local authentication and treats RSO as exploratory. No Riot approval is established here.

Owner decision on 2026-10-29: defer the Riot Sign On idea. Preserve this research for possible reconsideration; no implementation or Riot approval request is planned. The recommendations and integration outline below are conditional on explicitly resuming the idea.

## Assessment for Nashordaq

RSO could combine sign-in and verified Riot linking, remove manual Riot ID entry for ordinary accounts, and let participants avoid choosing a local username and password. It would simplify onboarding. It would not remove Nashordaq users, sessions, invitation access, administrator permissions or recovery. Supporting local authentication and RSO together would add code; removing passwords could save maintenance only after explicitly changing the standalone contract.

The current [user router](../backend/app/routers/user.py) resolves a submitted Riot ID and initializes ranked market data. It proves that an account exists with usable ranked data, not that the member controls that account. [Models](../backend/app/models.py) separate the user who owns a portfolio from the tracked player whose performance sets a share price. Keep that separation under RSO.

Recommendation: retain the current baseline while clarifying approval and deployment eligibility. After approval, trial RSO as an optional verified linking/sign-in method. A hosted deployment with a controlled domain is a better technical fit than arbitrary independent self-hosts. This is an architectural assessment, not Riot's stated approval preference. A later RSO-only participant experience would need a new accepted decision about recovery, availability and supported installations.

## Approval and eligibility

RSO requires an existing approved production application ID, followed by a separate RSO application. Production approval is therefore a prerequisite, not an OAuth credential automatically supplied with any API key. Riot's [RSO FAQ](https://support-developer.riotgames.com/hc/en-us/articles/22801670382739-RSO-Riot-Sign-On) describes the invitation to apply and a shared RSO client across approved game applications. The [OAuth client documentation](https://support-developer.riotgames.com/hc/en-us/articles/22897607341075-OAuth-Client-Documentation) explicitly requires both a functioning approved production application and a separate approved OAuth application before calls.

A personal API key is intended for a developer or small private community. It does not confer RSO eligibility. Production keys target larger communities and public products; public alpha/beta access cannot use a personal key. These are distinct access categories in the [portal API-key documentation](https://developer.riotgames.com/docs/portal#api-keys). The documents do not establish that a small LoL group can never obtain production approval, but they provide no guaranteed exception or small-group RSO route. This requires DevRel clarification.

The [production FAQ](https://developer.riotgames.com/docs/faqs#production-key-applications) generally requires a working website showing user flows, Terms of Service and Privacy Policy. A GitHub repository alone is insufficient. The LoL [production use-case guidance](https://developer.riotgames.com/docs/lol#use-cases-for-production-keys) also lists prototypes, mockups and presentations as evidence. Treat this as review guidance rather than a promise that an unfinished app qualifies. No approval date or implementation duration can be inferred.

## Credentials, callback and identity

An API key authorizes product API usage under its approved use case and limits. It is neither a player's login token nor the RSO client's credential. Riot describes a client ID plus client authentication material separately. Its [linked implementation tutorial](https://docs.google.com/document/d/e/2PACX-1vTSthxkWOIqPFe8Xqqjv4Ona5pRa5W3X6bLg4I47X15gJjG9ae-HU5a0by7VIVLWdPMgB9fTr5gvQcY/pub) says newer clients receive private-key JWT material; older clients may use Client Secret Basic.

That tutorial documents authorization-code flow: `/authorize` returns a `code` query parameter through a browser redirect; the server exchanges it at `/token`. The callback URI must be registered and repeated in the exchange. `openid` is required; `state` supports CSRF protection. It requires HTTPS while also showing a registered HTTP local-development example. That example does not establish production HTTP permission. The tutorial documents multiple registered redirect URIs, but no blanket wildcard, arbitrary hostname or dynamic-port entitlement.

For LoL, the [RSO integration page](https://developer.riotgames.com/docs/lol#rso-integration) specifies `GET /riot/account/v1/accounts/me` with an RSO bearer access token. Its Americas, Europe and Asia account responses are identical, so choosing the Europe API cluster does not identify EUW membership. The [AccountDto reference](https://developer.riotgames.com/apis#account-v1/GET_getByAccessToken) returns `puuid`, `gameName` and `tagLine`; the latter two can be absent. Region is not an AccountDto field. A normal Riot ID can therefore be populated without manual typing, but missing names need handling.

The [OAuth client documentation](https://support-developer.riotgames.com/hc/en-us/articles/22897607341075-OAuth-Client-Documentation) documents requesting `cpid` and reading it from `/userinfo` to obtain the current LoL platform ID. It also describes a LoL summoner `/me` endpoint, whereas the LoL integration page uses Account-V1. This source difference merits confirmation before implementation. Separately, the [Account-V1 reference](https://developer.riotgames.com/apis#account-v1/GET_getRegionByGame) lists `/riot/account/v1/region/by-game/{game}/by-puuid/{puuid}` for LoL/TFT active region. Neither route was exercised here. Confirm client permissions, current endpoint support and behavior for accounts without a LoL profile or after transfers.

## Tokens and continuing game data

The tutorial defines `offline_access` for refresh access and describes token expiry and refresh-token replacement. Inference: a one-time identity lookup followed by an application-owned session need not retain refresh tokens solely to keep that session alive. Later RSO calls would require a valid token, renewal or another login. This is a possible design choice, not a Riot session or revocation guarantee.

Login permission does not establish ongoing rank/match access. The [API reference](https://developer.riotgames.com/apis) lists `league-v4`, `match-v5` and a separate `lol-rso-match-v1`. The [portal](https://developer.riotgames.com/docs/portal#web-apis) assigns API access and limits to keys. Inference: ordinary background market updates can remain a separate API-key concern; do not assume `openid`, `cpid` or `offline_access` grants every gameplay endpoint. Confirm approved endpoint access and any consent requirements with DevRel.

RSO demonstrates control of a Riot account during authentication, not a unique human. It supplies no documented one-person guarantee. Inference: Nashordaq invitations, membership, administrator authorization and session revocation remain application responsibilities even if local passwords are replaced.

## Policy and unresolved deployment questions

The [General Policies](https://developer.riotgames.com/policies/general), marked updated May 29, 2025, require product registration and review of changes. They prohibit betting/gambling functionality under Monetization, prohibit games using Riot IP, disallow alternative skill-ranking systems, and restrict assets and competitive advantages. Non-cash-convertible currencies appear among permitted charging methods. That is not an exemption for a simulated trading market or Gamba. The [LoL policies](https://developer.riotgames.com/docs/lol#developer-api-policy) also restrict data brokerage and require protection of keys. Neither private use, virtual currency nor disabling Gamba alone proves approval. DevRel must assess the complete market mechanics, performance-based pricing, optional gambling and Riot assets.

Public sources do not settle whether independent self-host operators can share one RSO registration, whether each needs production/client approval, or whether an approved central authentication broker is permissible. Registered callbacks and protected credentials make arbitrary clone-and-run login an unresolved deployment issue. A broker is an architectural inference, not a documented requirement or approved workaround. Ask DevRel about deployment ownership, redirect registration limits, credential distribution, broker permission, small-group eligibility and the complete use case before selecting an implementation contract.

## Conditional integration outline

The existing FastAPI backend and Vite frontend can support this flow without another runtime service. A proposed backend RSO module would own authorization transactions, server-side code exchange and validated identity retrieval. [Authentication](../backend/app/auth.py) would continue to own users, invitations, administrator authorization and revocable sessions. The [Riot adapter](../backend/app/riot.py) and [scheduler](../backend/app/scheduler.py) would retain rank/match updates and their API-key boundary.

1. An invitation or signed-in linking action starts a short-lived browser-bound authorization transaction. The browser signs in on Riot's site; Nashordaq never receives the Riot password.
2. A registered backend callback validates the transaction, exchanges the code and retrieves the authenticated identity. Credentials and Riot tokens remain server-side. Use current [OAuth security practice](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1), including single-use state and code-injection protection. Confirm PKCE support for the approved client; validate signature, issuer, audience, expiry and nonce if consuming ID tokens.
3. Resolve a unique verified identity to the existing Nashordaq user, or create an invited member. Record the authenticated PUUID and refresh display names separately. Retrieve the platform through an approved route. Keep account authentication independent of ranked-data availability, which currently gates market onboarding.
4. Issue the existing application session. The frontend resumes its session check and loads game data. Cancellation returns to sign-in or the existing account. An RSO outage would prevent new RSO authentication, while existing application sessions can continue until expiry or revocation.

Do not convert today's manually entered Riot links into trusted login mappings or merge accounts by Riot ID. Existing members must authenticate locally and explicitly bind the verified Riot identity without losing balances, holdings, orders or aliases. Define duplicate-identity and account-switch behavior before implementation. The current model has no unique verified PUUID identity, so persistence changes require a supported schema/update path. Riot [documents encrypted identifiers per API-key holder](https://www.riotgames.com/en/DevRel/player-universally-unique-identifiers-and-a-new-security-layer); confirm identifier compatibility across the approved RSO/API registrations and migration, rather than assuming IDs survive a change of key owner.

The existing session cookie uses `SameSite=Strict`. A callback cannot rely on receiving it after the cross-site Riot redirect. Bind the authorization transaction through a dedicated short-lived callback-compatible cookie, following [cookie behavior](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#samesitesamesite-value), then rotate the application session. Preserve the existing mutation CSRF protections; the callback needs its own validated OAuth transaction. A central broker would add another trusted service and require a separate design and Riot permission.

Before release, verify an actual approved-client round trip, invited registration, explicit existing-account linking, duplicate rejection, cancellation, invalid/replayed state, code-exchange failure, absent names/LoL profile, and unchanged operator/demo access. Check the real redirect/cookie behavior in a browser and background updates after OAuth tokens expire. This investigation changed documentation only. No live RSO flow, approval, migration or deployment was tested.
